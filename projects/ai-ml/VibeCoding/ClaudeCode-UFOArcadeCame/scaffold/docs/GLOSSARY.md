# Glossary

**A reference of key terms used throughout the project documentation, code, and gameplay.**

| Term | Definition | Source Doc(s) |
|---|---|---|
| **Vanguard** | The player character — an original shield-throwing hero at the bottom of the playfield. Controllable via arrow keys. | PRD §F1, §F9, ADR-0004 |
| **Sentinel** | An enemy robot. Sentinels spawn in a formation, descend toward the player, and fire lasers. Regular Sentinels have HP ranging from 1–4 hits depending on level; bosses have higher HP. | PRD §F3, §F4, ADR-0004 |
| **run** | One full playthrough attempt from level 1. A run ends when the player wins (clears level 10) or loses (3 lives exhausted or formation reaches the player's row). Restarting the game via the pause menu starts a new run. | PRD §Summary, terminology note |
| **level** | One stage of play consisting of a single enemy formation to clear. The game has exactly 10 levels. Clearing all enemies in a level's formation advances to the next level (or triggers victory after level 10). | PRD §F5, §Summary |
| **formation** | The block of enemy robots arranged in a grid (rows × cols). The formation moves as a rigid unit left/right, steps down when hitting a screen edge, and advances toward the player over time. | PRD §F3, architecture component responsibilities |
| **hitsToKill** | The number of shield hits required to destroy a single enemy. Ranges from 1 to 4 for regular enemies; bosses can have higher values (up to 12 at level 10). Also called "HP" colloquially. | PRD §F4, `src/core/types.ts` Enemy interface |
| **boss** | A unique, tougher enemy that appears in levels 2–10 (level 1 has no boss). Bosses have higher `hitsToKill` than regular enemies in the same level. Example: level 2 boss has 2 HP; level 10 boss has 12 HP. | PRD §F4 (10-level table), types.ts |
| **shield** (projectile) | The projectile thrown by the player when pressing space. Travels upward and damages the first enemy it hits. Infinite supply; only gated by a 250 ms throw cooldown. | PRD §F2, constants.ts THROW_INTERVAL_SECONDS |
| **power-up** | A collectible drop that falls from a destroyed enemy. The player must catch (collide with) it to activate its effect. Four types exist: HIT_POWER, SPEED, SHIELD, PERMANENT_MULTIPLIER. | PRD §F7 |
| **HIT_POWER** | A temporary power-up type: while active (8 seconds), each shield hit deals 5× damage. Effect is paused during game pause, resets if a new HIT_POWER is caught while one is active (same-type refresh), and composes multiplicatively with the permanent multiplier. | PRD §F7 AC4, AC8, AC9 |
| **SPEED** | A temporary power-up type: while active (8 seconds), the player's horizontal movement speed is 3× base. Effect is paused during game pause and refreshes on catch. | PRD §F7 AC5, AC8 |
| **SHIELD** | A temporary power-up type: while active (8 seconds), the player is invulnerable to enemy lasers (no life loss on hit). Effect is paused during game pause and visibly distinguished (non-color-only per NFR-9a). Also called "Indestructible Shield" in some contexts. | PRD §F7 AC6, NFR-9(a) |
| **PERMANENT_MULTIPLIER** | A permanent power-up type: on catch, the player's current hit power is multiplied by 1.8 permanently for the rest of the run. Multiple catches stack multiplicatively (two catches = ×3.24 = 1.8 × 1.8). Reset only on Restart Game or a new run. Visible in the HUD. | PRD §F7 AC7, AC10 |
| **guaranteed drop** | One power-up per level is guaranteed to drop from a random enemy when it is destroyed. Additional drops beyond the guaranteed one occur at a 10% probability per enemy death (a tunable default). | PRD §F7 AC1 |
| **i-frames** | Short for "invulnerability frames." A brief post-hit invulnerability window (tunable, default 1.5 seconds) during which the player is immune to enemy laser damage and visibly distinguished (non-color-only). Not the same as the SHIELD power-up effect; this is automatic after any hit. | PRD §F8 AC9, NFR-9(a) |
| **Game Over** | Terminal state reached when the player loses: either lives reach 0 or the enemy formation reaches the player's row. Displays a clear Game Over message with an option to restart. If both loss conditions occur in the same frame, the game resolves to a single deterministic Game Over (not two competing screens). | PRD §F8 AC4, AC5, AC8 |
| **Victory** | Terminal state reached when the player wins: clearing all enemies in level 10. Displays a distinct win screen (visually different from Game Over), reads as a deliberate conclusion (not an abrupt cutoff), and offers an option to start a fresh run. | PRD §F8 AC6 |
| **pause / PAUSED** | Game state entered by pressing Esc during active play. Freezes all motion (player, enemies, projectiles, power-ups, timers). Pressing Esc again or selecting Resume continues exactly where the player left off with no loss of in-level progress. | PRD §F6, GameStateMachine |
| **screen state machine** | The explicit state machine managing the game's five screens: TITLE (start), PLAYING (active gameplay), PAUSED (pause overlay), GAMEOVER (lose state), and VICTORY (win state). Input is routed per-screen so Esc means different things on different screens. | ADR-0002, GameStateMachine.ts |
| **fixed timestep** | A game-loop pattern where simulation advances in fixed-size time steps (1/60 second in this game) regardless of the real wall-clock frame rate. Decouples simulation from rendering, ensures determinism, and prevents frame-rate-dependent physics bugs. The accumulator loop in `GameLoop.ts` implements this. | ADR-0002, GameLoop.ts |
| **World** | The single mutable object holding all game state: player position/timers, enemy array, projectile array, power-up array, effect timers, formation position/direction, lives, score, current level, and screen state. All systems read and mutate this object each tick. | `src/core/types.ts` World interface |
| **system** | A pure-ish function that updates a specific aspect of the World each tick (e.g., MovementSystem, FormationSystem, CollisionSystem). Systems execute in a fixed, deterministic order so complex multi-system interactions (like two loss conditions in one frame) resolve consistently. | architecture component responsibilities, ADR-0002 |
| **LevelConfig** | An immutable data structure (one row per level) encoding the 10-level progression: formation size (rows × cols), enemy HP mix, boss HP, formation speed multiplier, fire-rate multiplier, and guaranteed power-up drops. Read by systems; never branched-on in code. | ADR-0003, `src/config/levelConfig.ts` |
| **formation-approach warning** | A visual danger cue that appears when the enemy formation's lowest living enemy is one row above the player's row (F3 AC6). Combines a pulsing border and a shape/text cue (non-color-only per NFR-9a). The instant loss rule (formation reaching the player's row) remains unchanged; this is a one-row-early cue only. | PRD §F3 AC6, Open Question Q7 |
| **HUD** | Heads-up display: the on-screen persistent UI showing the player's current score, lives remaining, current level, permanent-multiplier readout, active-temporary-effect indicators, and the one-line control hint. Rendered as DOM overlays over the canvas in a reserved band with guaranteed contrast (NFR-9b). | PRD §F10, §F8 AC1, §F7 AC10, §F7 AC11, NFR-9(b) |
| **NFR** | Non-Functional Requirement. PRD §NFR-1..NFR-10 define performance, compatibility, accessibility, and IP constraints that transcend individual features (e.g., "load ≤3s," "60 FPS," "no licensed IP"). | PRD §Non-Functional Requirements |
| **ADR** | Architecture Decision Record. Documents a major design decision, its context, the chosen option, alternatives considered, and consequences. The project has 5 ADRs covering stack/rendering, loop/determinism, level data, art/IP, and instrumentation. | `docs/architecture/adr/` |
| **traceability** | The practice of linking code, tests, and docs back to the upstream requirements that justify them. Every feature in the PRD traces to market goals/use cases; every ADR traces to PRD requirements; every test traces to acceptance criteria; every final doc references its sources. | `traceability-conventions` skill |
| **canvas (or Canvas 2D)** | HTML5 graphics API for drawing 2D shapes, text, and images directly to a raster surface. Used here for all game-field rendering (entities, projectiles, backgrounds) to achieve 60 FPS with minimal overhead. HUD overlays are DOM. | ADR-0001, CanvasRenderer.ts |
| **procedural art** | Art generated by code (draw functions) rather than external image files or raster sprites. All sprites in this game (shield, Vanguard, Sentinels, lasers, power-ups) are drawn procedurally as vector shapes, keeping asset load near-zero and making IP compliance auditable. | ADR-0004, `src/render/shapes.ts` |
| **instrumentation** | Lightweight telemetry emitted during play to track events like "session started," "level reached," "power-up caught," "run restarted." Stored in browser localStorage as anonymous integer counters; never sent to a server. Supports NFR-8 (observability of market goals B1–B4/P1–P5). | PRD §NFR-8, architecture §Data Flow, `src/instrumentation/Instrumentation.ts` |
